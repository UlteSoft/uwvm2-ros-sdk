# Separate Wasm modules and a real archive

This source candidate requires the common qualified `set_kind` implementation. Run `xmake` here: main/main_cpp are binary Wasm consumers; io, algorithm and ros_comm are separate shared Wasm modules; algorithm_core is a real relocatable Wasm archive linked through `add_deps`. A coerced target kind refuses before build. No application build is treated as library evidence. The dynamic deployment requires four Wasm files: main plus io, algorithm and ros_comm. The archive is a build input and is not deployed.

io performs actual WASI stdout with its own memory. algorithm calculates unsigned arithmetic through an extracted archive member and explicitly checks an ungranted ROS acquisition. It keeps the default WASI policy, which includes basic standard-stream rights, and has no additional resource/ROS grants. ros_comm alone owns the exact original two-field RobotStatus observation, its native ROS capability, bounded polling/clock wait and one close. Modules exchange only fixed u32 scalars; no capability or linear-memory pointer crosses module boundaries. Main and library mutable state must be called serially.

The complete preload and manual Single policy is in `manual-run.sh`; inspect it and set `UWVM_EXECUTABLE`, `SDK_GATEWAY_SOCKET`, `SDK_GATEWAY_UID`, `DOBOT_NATIVE_IDENTITY` and `DOBOT_CODEC_IDENTITY` before invoking it from this example directory. The script uses the target-specific `build/targets/<encoded-target-name>` output paths created by the shared Xmake rule. Each `--wasm-preload-library` rename is the exact identity used by `--wasip1-single-create` and `--ros2-single-create`. Only ros_comm is enabled/granted native ROS; there is no ROS global grant. The native identity comes from independently installed native metadata; set the adapter codec identity from the same compiled paired manifest. A matching custom registry/runtime/gateway and controlled original ROS peer must already be running; enabled targets preflight the real gateway before guest entry. No robot hardware is involved. This script is never an automatic `xmake run` hook.

Positive acceptance must compare both original Boolean fields and the complete two wire bytes against the independent native publisher, the actual computed score, primary/cleanup status and algorithm_denied=13. Also run main_cpp against the same C producers for cross-language evidence. `wrong_signature` requests i64/i64 from the i32/i32 score export: preload algorithm and run it with no ROS target enabled; loading must refuse before main. Duplicate module renames must refuse as well. Inspect the actual `.a` member list and symbols using the common pinned llvm-ar/llvm-nm and verify extraction into algorithm. Repeat transitive dependencies, signature/width/collision rejection, module-owned memory and explicit denial checks for both guest widths and x86/QEMU ARM. Core preload support does not imply LLVM PIC/dylink support.

Controlled Linux x86 acceptance covers wasm32/wasm64 Preview1 without threads or exceptions: 16 cold targets, two real archives, six shared modules, C/C++ consumers and arithmetic/refusal paths. A source-paired Jazzy runtime/gateway also passed native RobotStatus observation, per-module permissions and cleanup in both widths. The public Xmake declaration retains Humble; that native installation and QEMU ARM require separate acceptance. Wrong-signature initialization follows the maintained runtime's fatal SIGILL diagnostic. Core Preload qualification does not establish PIC/dylink support.
