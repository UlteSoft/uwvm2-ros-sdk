# Kinova frozen C0 public Stage A candidate

This source candidate registers four mandatory cases with the installed SDK simulation API v1. It has not passed public `xmake` or `xmake test`. The separate private R210/R212 observations do not grant public acceptance.

Run `xmake` from this example directory to stage the hash-pinned installed Wasm; this build step does not execute it or require a live deployment. Run `xmake test` on the admitted Linux host. Use the current VM-owned live producer to supply `UWVM_ROS_SIMULATION_ADMISSION` and `UWVM_ROS_SIMULATION_DEPLOYMENT`; the application does not create either document. The existing shared launcher must qualify the complete folder, actual after-exec actors, canonical lock lifetime, common 64 GiB ancestor and zero swap before a payload run.

The real binary target consumes the complete installed 4,449-byte `joint-step.wasm`, SHA-256 `c0d886e864243938999e4adf4c0f4ce6fb3c2c001723b855cd8b203bfafe2043`. It does not rebuild the guest or build a native SDK observer. Input identities are in `profiles/input-identities.json`. This candidate is specific to the R12 runtime and native450 boundary. Replacing either requires a new explicit identity and qualification.

`SDK04_KINOVA_ENVIRONMENT_INPUTS` selects ordinary scene data described by `profiles/environment-inputs.schema.json`. That file, its official program files, the VM-owned native host, its actual provenance and every mapped dependency must already be pinned in the live deployment's existing `official_provider_files` or `runtime.paired_providers`. This scene data is not an admission, generation setter or revocation API. `profiles/runtime-arguments.json` declares the expected existing native CLI templates for the four scenarios.

The actual execution order starts with permission denial: C0 must exit 13 before any native endpoint. The normal case must exit 0 after a real goal/result, two fresh guest state copies and all seven guest target assertions. A mismatched real native authority reference must exit 110 with no goal/state; a helper killed and reaped before C0 starts must yield 38 with no goal/state. These two error codes follow the actual restricted client transport. The driver calls `Context.complete_operation_case` in every case; it never fills completion state or supplies an alternative verifier when the installed common consumer blocks a missing negative profile.

The environment expands unchanged official `ros2_kortex` Gen3 seven-axis external-cable Xacro at commit `462dab9aa4732d733be55e1846530dd920c7c7d3`, with `mock_components/GenericSystem`, official controller manager, robot-state publisher, joint-state broadcaster and trajectory controller. The expected expanded model SHA-256 is `bc2794800551813d930d1cb729b6b3a7230fff559628188df1ef8fc6ac37992d`. This is a software mock. Gazebo/Isaac physics and sensors remain mandatory separate work.

The driver uses installed `Context.guard`, `spawn`, `run_vm`, `events` and `complete_operation_case`. Native ROS client work stays in the pinned VM-owned restricted host; SDK application logic stays in the frozen Wasm. The prior quarantined `official_joint_step` implementation remains quarantined.

Open gaps include independently attributable authority fields, expired/already-open guest handles, stale feedback replay, two/three private component instances, typed channel isolation, full Stage B, all original model/release/language/library/architecture/security/debug/cache/update/performance rows and the final SDK10 world-model scenario. A four-case pass cannot close those requirements.

Official source bytes and the full upstream LICENSE are retained under `vendor-prefix/share/kortex_description`. Additional provenance and source-only status are retained in the SDK04 qualification workspace.
