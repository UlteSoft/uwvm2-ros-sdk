Current 5.0 requires the NVIDIA Lyrical buildfarm on Ubuntu 24.04. The 4.6 profile uses Jazzy. Both list Ampere-or-newer x86 GPUs with at least 8 GB VRAM, CUDA 13.2+ and driver 595+; DGX Spark is a separate DGX OS tuple. These requirements do not follow from ordinary ROS or generic arm64 support. [5.0 platform requirements](https://nvidia-isaac-ros.github.io/v/release-5.0/getting_started/index.html), [4.6 platform requirements](https://nvidia-isaac-ros.github.io/v/release-4.6/getting_started/index.html).

The 3.1 top-level table and compute guide disagree about Ampere versus Volta. The 4.1 setup instructions name L4T R38 revision 2.2 while the JetPack archive lists 38.2/38.2.1 for 7.0. These conflicts remain explicit blockers for the exact tuple. Old 2.1/Focal packages are no longer available from the discontinued buildfarm; the historical source/profile remains required. [3.1 compute guide](https://nvidia-isaac-ros.github.io/v/release-3.1/getting_started/hardware_setup/compute/index.html), [4.1 setup](https://nvidia-isaac-ros.github.io/v/release-4.1/getting_started/index.html), [JetPack archive](https://developer.nvidia.com/embedded/jetpack-archive), [2.1 notice](https://nvidia-isaac-ros.github.io/v/release-2.1/getting_started/index.html).

5.0 replaces the old NITROS client/type packages with rosidl::Buffer and the CUDA buffer backend; its remaining bridge is deprecated. The pinned 4.6 tree still has NITROS packages. Direct API users require source migration and separate message/container/backend ABI checks. A topic name or latest header does not establish historical compatibility. [5.0 release notes](https://nvidia-isaac-ros.github.io/v/release-5.0/releases/index.html), [migration guide](https://nvidia-isaac-ros.github.io/concepts/rosidl_buffer/nitros_migration.html).

The single-executable link goal applies to the real produced VM. CUDA supports static runtime/device runtime libraries, but real GPU execution still needs a matching NVIDIA driver and device stack. A toolkit libcuda stub cannot satisfy that dependency. Historical GXF source has a static wrapper while installing/linking shared core and extension libraries. Those shared libraries need a justified exact closure or a separately qualified static solution. [CUDA compiler options](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html), [driver compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/latest/index.html), [pinned GXF build](https://github.com/NVIDIA-ISAAC-ROS/isaac_ros_nitros/blob/91732780c48bfbb4dde15712c45151e0839428af/isaac_ros_gxf/CMakeLists.txt).

Static TensorRT support is version- and architecture-specific. The 8.6.1 sample guide documents Linux x86 static builds and excludes AArch64 for that route; 10.11+ deprecates static libraries, with removal in 11.0. This does not decide the exact selected Isaac/TensorRT package closure. VPI also needs its actual target libraries and release-specific license audit. [8.6.1 static sample guide](https://docs.nvidia.com/deeplearning/tensorrt/archives/tensorrt-861/sample-support-guide/index.html), [TensorRT transition](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/getting-started/release-notes-10/10.14.1.html), [VPI EULA](https://docs.nvidia.com/vpi/EULA.html).

The root NVIDIA software license and component notices must be retained per exact tag/package. An Apache header on a build file does not license every NVIDIA binary in its dependency graph. CUDA lists specific redistributable runtime files under its own conditions; VPI, TensorRT, GXF and third-party components need their own exact terms. No binary redistribution is approved by this source report. [Pinned root license](https://github.com/NVIDIA-ISAAC-ROS/isaac_ros_common/blob/7bec6ae5dbb2faa11617f40226e8932a4a94e6e4/LICENSE), [CUDA attachment A](https://docs.nvidia.com/cuda/eula/index.html).

All five requested runtime targets remain visible. x86_64 and aarch64 need exact hardware/provider tuples. i686, arm soft-float and armhf have no established supported Isaac tuple in this audit; ordinary ROS support and historic TK1 CUDA do not establish one. Their general VM target work remains required.

No final ELF glibc floor has been measured. Ubuntu labels and CUDA-supported OS tables are context, not the final GLIBC/GLIBCXX/CXXABI symbol requirement. Qualification must inspect PT_INTERP, DT_NEEDED, RPATH/RUNPATH, explicit and implicit providers/helpers, then execute that exact asset in the promised minimum-glibc environment. A private native ROS helper remains a blocker for the single-VM executable claim.

All SDK business, client calls, callback/state/sensor processing and file I/O must run inside Wasm through the VM permission and operation audit. Removed SDK-native applications are not runtime dependencies. Linux public xmake/xmake test, unchanged complete Wasm across compatible vendors, official simulation, multilingual composition and the real world-model application remain mandatory and unqualified.
