# 旧 ROS 包迁移到 Wasm：实验边界与验收单位

目标是逐步迁移尽可能多的旧 ROS 包及其可移植依赖，减少原生可信计算面。
Wasm 不是只包住一个调用原生 ROS 业务服务的客户端。算法、状态、消息处理、
控制决策和可移植的上层 ROS 支撑逻辑应进入 uwvm2-ros。Native ROS 接口及其
RMW/DDS 通信链路保留为可信的授权、额度控制与审计出口；设备和必要系统入口同样受宿主授权。

本文区分当前实验已经覆盖的范围与目标架构。它不把成功编译或有限仿真等同于整包兼容，
迁移范围以保留 ROS 语义级审计为前提，不以删除全部原生 ROS 代码为完成条件。

## 一个通过结果究竟代表什么

每项实验必须记录上游包名、发行版、准确提交、完整原始输入、适配补丁和执行配置。
仓库、包、类、函数、示例、语言绑定和厂商模型是不同的计数单位。
同一组件的多语言示例、五个平台或十三个模型通过，不能重复计为迁移了多个 ROS 包。
“9000 多个包”是目标规模；覆盖率必须使用另行冻结、按版本标识的真实包清单及其依赖图。

当前 PID 与 Trajectory 实验的验收单位均为 source-component：

- control_toolbox 4.11.1 的 control_toolbox::Pid。计算、增益检查、反饱和、异常和诊断保留；
  删除两个 rclcpp::Duration 便捷重载，使用显式串行值容器替换原生实时互斥容器。
  不能据此宣称并发增益更新、优先级继承、PidROS 或整个 control_toolbox 包已经迁移。
- ros2_controllers 4.42.1 中 joint_trajectory_controller 包的 Trajectory。
  保留轨迹采样、插值和角度处理，改用私有消息/时间值类型。
  这不是完整 JointTrajectoryController 插件、controller_manager、
  FollowJointTrajectory action 服务或整个 ros2_controllers 仓库的迁移。

因此，这两项实验对“完整 ROS 包已迁移”的计数贡献目前是零。它们证明可复用的
源码移植路线，不能把尚缺的包接口和语义隐藏在成功的算法测试后面。

PID 与 Trajectory 的 portability.json 记录具体删改、并发前提、内存模型和未迁移功能。
portability_contract.py 检查原始源码摘要、全部组件输入和完整补丁；构建时调用此检查。
该工具只证明源码身份和补丁完整性，不证明算法等价、运行安全或整包兼容。
这些结论必须分别由原生对照、真实 Wasm 执行、权限/隔离测试和集成证据支持。

## 不依赖 ROS 中间件的对照：angles

angles 1.16.1 的 C++ 头文件、Python 包及其 9 项 C++ / 7 项 Python
原始测试保留原始字节。C++ 和完整 CPython 语言引擎均进入 Wasm；
本实验不通过原生 ROS 算法服务或宿主 Python 执行业务逻辑。
这验证库源码无需修改时的迁移路线，而不是仅替换算法的演示。

原始 ament/CMake、包发现、安装导出、Python 安装布局和下游 ROS
工作空间兼容性尚未验收。Xmake 构建适配不能自动等同于这些能力。
因此仍不把该实验计为完整 ROS 包迁移；运行功能和构建部署分别记录。
具体测试框架特性、原始 Python 警告及可选权限探测见
src/platform/ros2/angles/README.md。

## 当前实验的实际分界

Wasm 内执行原始 PID 与 Trajectory 组件、私有状态、有限轨迹与取消决策、
ROS 消息编码和业务断言。C/C++ 标准库与异常运行库也编译成 Wasm，
不存在以原生 PID/轨迹计算服务替代 guest 算法的回退路径。

官方模型测试的原生侧仍运行：

- 官方物理引擎、模型自带执行器和设备读写。
- 设备适配器中的 rclcpp 节点/执行器、消息类型支持、RMW/DDS 通信。
- Gateway、VM、操作系统以及测试进程监督。

第二项属于本项目保留的受控 ROS 通信基础设施，承载可信的授权与审计出口。
该侧只承载受授权的通信与必要适配，不承接本应在 guest 内执行的规划、PID、
轨迹计算或其他业务决策。官方模拟器自身用于独立对照，
其留在原生侧不构成旧 ROS 包迁移成功或失败的结论。
实际进程映射和适配器源码身份须一并记录；仅扫描动态库名不能发现所有静态链接逻辑。

## 可移植性边界不是按包名划线

纯算法、规划、滤波、状态机、序列化、协议状态、参数验证以及消息值处理，
通常可以随其依赖重新编译为 Wasm。平台专属 SIMD、汇编或系统 API
需要保留语义的适配与独立测试；不能用结果不同的替代算法冒充原模块。

节点、topic/service/action、参数、生命周期、日志、时间和执行器属于下一层迁移。
需要明确支持的 ROS API 与语义范围：QoS、发现、回调顺序、时钟域、取消、
错误返回和关闭流程都属于功能。当前桥接接口并不自动提供完整 rclcpp/rclpy 兼容性。
原始语言运行库也必须在 Wasm 内运行；把 Python/Ruby/C++ 业务留在宿主不能计为迁移。
ROS1 与 ROS2 均保留受审计的 native 通信出口。厂商协议的业务处理可继续迁移，
实际通信必须走明确授权和审计的接口。只有原生闭源二进制、
缺少可重编译实现的依赖，应列为输入/实现缺口；保留桥接不等于完成移植。

线程、优先级继承、共享状态、原生插件和跨进程共享内存属于需要额外 ABI/调度适配的依赖。
可以在有证据的前提下重构或限制执行配置，但必须声明行为变化。
将并发模块串行化仅能验证串行子集，不能称为完整等价。
现有 ELF .so 不能直接作为 Wasm 动态库；必须从源码重新构建并验证初始化与所有权。

内核设备、DMA、硬件中断、现场总线系统调用、真实 GPU 提交等宿主入口，
通过最小且受控的能力接口保留。其前后的算法、数据验证和状态机仍应评估移植。
“暂时缺少 Wasm 工具链/适配器”和“本质需要宿主硬件入口”是两类不同障碍。

## Native ROS 是授权与审计边界

本项目当前采用的边界是：
Wasm 业务／可移植上层 ROS 逻辑 → VM 的 native ROS 权限与审计接口 →
受控 native Gateway／RMW／DDS → 原生 ROS 对端或设备。

RMW/DDS 保留在这条原生通信链路中，不列入本次 Wasm 迁移目标。
这里的选择依据是本项目的可信审计架构，并非宣称 DDS 在技术上无法实现为 Wasm。
迁移一个 ROS 包，不要求把该宿主通信依赖也删除；但不能把原生算法服务作为
包内业务逻辑的执行替身。

每次 ROS 语义操作必须携带 VM 确定的调用模块身份，并在可信边界处理接口是否
暴露、调用是否允许、资源与句柄所有权、人工配置的额度、返回结果和审计记录。
发布/订阅、service/action、参数及其他已提供的 ROS 操作遵循同一边界。
跨模块调用不能增加授权，也不能由 guest 自报身份来选择另一模块的权限。

不得以 guest 直接运行 DDS、开放原始网络、另设未经审计的宿主接口或原生
业务代理绕过这条 ROS 授权链。厂商特有的通信也需要显式定义可审计操作及其
资源权限；协议业务处理进入 Wasm 不等于获得任意网络和设备权限。

宿主审计与功能迁移分别验收：原始业务结果、错误/取消/退出语义、实际原生对端
互通，以及允许/拒绝/限额/跨模块调用的审计归属都必须可核对。
保留 native ROS 审计出口不降低整包公共接口和依赖闭包的迁移验收标准。

## 三种库模型分别验收

静态库是实际 Wasm 对象归档，最终链接进一个实例。其指针、分配器、栈、
函数表和异常运行库由消费者共享。同一实例内部的库不是安全隔离边界。

同内存 preload 动态库由不同模块引用同一个 memory 对象，属于同一信任域。
必须定义数据重定位、栈/分配器、函数表、初始化顺序、回调和异常 ABI。
共享同一个非 shared memory 对象，不等于开启 Wasm threads/atomics。
普通 core-preload 模块各自拥有内存，也不等于同内存动态库。

独立内存组件拥有不可向对方暴露的私有内存，可以另外持有显式通信 memory。
跨边界传递经过验证的值或有所有权的句柄，不能把 C/C++ 私有指针交给另一实例解引用。
multi-memory 本身不会自动完成复制、长度/溢出检查、生命周期、重入或并发协议。
通信内存的边界检查也不能代替各模块的 WASI/ROS 独立授权。

当前 PID 与 Trajectory 两个 C++ 组件只实现静态形式；angles 使用编入实例的头文件与源码包。同内存动态和独立 multi-memory C++ 形式尚未实现，
SDK 必须明确拒绝这些配置。独立 WAT 示例验证 VM 的内存语义，不代替 C++ ABI 验收。

现有跨语言库示例还使用受限的标量调用约定，例如 apply(i32, i32) 的结果与错误码、
close 的状态释放，以及每个目标一个直接语言库依赖。这些测试证明其声明的
调用闭包，不证明任意 Python 对象、C++ 类、ROS 消息、回调或线程可以跨模块传递。
不能把这种示例 ABI 当作数千 ROS 包的通用迁移层。

## 从组件到完整包的递进证据

组件通过后，继续迁移它的剩余接口和依赖，使用原包的公共测试加上原生对照。
完整包验收须覆盖声明支持的公共功能及依赖闭包：正常结果、错误/异常、取消/退出、
状态所有权、消息语义以及所需执行配置。适配掉的功能必须列为不支持，
不能返回成功的空实现。必要宿主接口保持显式授权，未迁移的原生业务依赖继续计入范围。

解释器与 LLVM JIT 执行同一 Wasm 制品，分别验证五个目标平台。
未授权、仅暴露而拒绝、明确允许、人工设置额度、跨模块越权和错误后的继续执行
应有与功能对应的检查。有限测试不能证明所有输入绝无缺陷。

仿真结果应同时列出模型、被测功能和剩余依赖。官方模型闭环通过是集成证据，
不是厂商认证、真实机器人准入或全包覆盖率。不得为使结果通过而修改原模型的
质量、重力、限位、接触或执行器行为。

## 效率结论也要保留边界

原版 native、适配后 native、相同源码的 Wasm 至少三方对照。
这样才能分清串行化或类型适配带来的变化与 VM 执行代价。
分别记录编译/启动、首次调用、稳态计算，以及通信与物理模拟时间；
不把长循环的快速度解释成冷启动快，也不把 native DDS 成本算成 Wasm 算法成本。

性能只在本机 x86_64 测量，固定输入、输出校验、编译选项、制品摘要和 CPU 条件，
复用已安装 VTune 的硬件热点与微架构分析。JIT 符号/源码未解析时应明确报告，
不能从 unknown 热点虚构源码归因。QEMU 只提供其余架构的正确性证据。

规模化应按真实依赖图推进：优先形成可复用的标准库、ROS 值类型、消息、
节点/执行器与库 ABI 适配，再逐包验证。一个通用依赖迁移可以帮助多个包，
但这些包仍需各自通过功能与依赖闭包验收。
