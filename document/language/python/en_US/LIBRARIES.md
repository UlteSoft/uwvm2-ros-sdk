# Genuine interpreter libraries

QuickJS 2026-06-04, CPython 3.14.8 and Lua 5.4.8 share one compiler and core implementation per language and target width. Ordinary Xmake `set_kind("static")`, `set_kind("shared")` and `add_deps` select archive, preload-module and application linkage. The current bounded ABI provides a source-defined `apply(a, b)` and explicit `close`; it does not declare arbitrary exported functions or pointer transfer.

Use `set_ros_platform("wasi")`, `set_arch("wasm32")` or `set_arch("wasm64")`, and `set_plat("wasm-wasip1")` for these computation libraries. Lua requires `set_wasm_exceptions("eh")`. All targets in a dependency graph use the same exact width and exception profile. Native ROS commands without library dependencies retain the complete separately versioned ROS module bundle. A ROS-aware interpreted consumer of these libraries is still pending.

A JavaScript library defines `globalThis.apply`, a Python library defines `apply`, and a Lua library defines the global function `apply`. Both arguments and a successful result must be exact signed 32-bit integers. The actual language engine evaluates the source and executes the function. The exported Wasm function has `(i32, i32) -> i64`: upper 32 bits contain errno, lower 32 bits contain result bits. Errors are 12 for allocation, 16 for rejected reentry/ownership and 22 for a source exception, invalid type or range. A failed call commits no result. `close() -> i32` releases that library's owned language state; a later apply creates fresh state. Repeated close is safe.

The initial source binding consumes at most one direct library dependency per target; linear transitive chains are represented by ordinary `add_deps`. JavaScript receives `__foreign`, Python imports `_foreign`, and Lua receives `__foreign`. Each binding supplies `apply`, `close` and the compatibility `initialize` hook. This hook performs no reactor startup: the common Wasm start section owns startup exactly once. The result is an exact BigInt in JS, integer in Python and signed integer in Lua. The current errno/result range fits that Lua integer.

Exports use `uwvm_` followed by the hexadecimal bytes of the namespace-qualified Xmake target identity, then `_apply` or `_close`. The exact names and source/artifact SHA-256 values are recorded in `.uwvm-ros/genuine/<identity>/source-abi.json`. The common artifact receipt lists each actual preload identity and module file. For a target named `algorithm`, use the literal identity `algorithm` when creating its WASI Single and preloading it. Manually specify `--wasip1-single-create algorithm --wasip1-single-noinherit-system-environment algorithm --wasm-preload-library <algorithm.wasm> algorithm`; repeat explicitly for other modules, then `--wasip1-global-noinherit-system-environment --run <main.wasm>`. A wasm64 deployment also explicitly enables memory64 and table64; Lua additionally enables exceptions. Deployment permissions are supplied by the user and are never expanded by the build adapter.

A shared module owns its memory and table. Values alone cross its boundary; no source object, pointer, borrow or native handle escapes. Static linkage shares memory and runtime authority, and has no module isolation. Python static libraries use one genuine core manager with separately owned stock subinterpreters. Default WASI includes basic standard streams; this computation example requests no additional resources or ROS capabilities.

The adapter exposes source and bounded ABI support for review. Acceptance depends on the delivered source's measured build/runtime receipts. Broader dependency graphs, arbitrary function signatures, io/algorithm/ros_comm permission examples, native ROS observation, QEMU AArch64 execution and ARM-host compiler qualification remain separate requirements.
